# Yougori

Use `yougori`, a same-user local client of the Yougori runtime. In a source checkout use `npm run cli -- <arguments>`. Read [the CLI guide](references/cli.md) for examples, lifecycle, and permission boundaries.

The desktop CLI's **Skills → Install skill** and `yougori skills install` put this skill in `Yougori/Workspace/skills/yougori` under the user's home. Ask the agent to read that folder's `SKILL.md`; automatic discovery is agent-specific. **Copy agent guide** provides the same instructions. Setup does not install or sign in to an AI agent.

Before choosing anything for the user, read their preferences: `yougori prefs show` (the user's `~/.yougori/PREFERENCES.md` and the project's `.yougori/PREFERENCES.md`; the project wins). Preferences suggest a choice but never grant permission. Ask before a billable, public, destructive (delete, reset, restore), credential, PC-folder, or Full control sharing action when the user has not already authorized that specific action and scope in the conversation. Do not ask again for an action they already authorized. After the user confirms a choice they want remembered, run `yougori prefs remember KEY VALUE` (add `--project` for this project only). Never store passwords, tokens or keys there.

The desktop app and the CLI share one engine: anything created in either appears in both, including saved domains and model conversations. `yougori status` shows everything at a glance.

For compute work, start with `yougori agent inventory`. It returns exact environment IDs, current states, local CPU/RAM allocations, GPU flags, managed-provider details, and per-target command/file capabilities without returning platform secrets. Treat `ready` as a capability check, not a grant to take unrequested action. For a local OCI workload use `yougori run -d --name NAME IMAGE`, then `yougori cp PATH ENV_ID`, `yougori exec ENV_ID COMMAND...`, `yougori logs ENV_ID`, and `yougori stop ENV_ID` when the work is done. Pipe output or use `-d` so `run` returns one finite JSON result; interactive `-it` requires a terminal. `logs` returns a JSON `logs` field, and `exec` returns stdout, stderr and the guest exit code. For managed cloud compute, run `yougori neocloud prices --format json` and inspect the provider status. Put a proposed resource in a JSON file as `{"request":{"provider":"vast","product":"gpu","name":"training","image":"ubuntu:24.04","offer":"123","diskGb":20}}`, then run `yougori neocloud plan --file FILE` for provider-specific validation. `plan` does not check account access or live pricing. Use `quote`, `create`, `inspect`, `start|stop` and `delete` with exact IDs after review. An hourly compute quote is not the total bill; stopping may leave charges. Some providers are listed but not integrated. Never present an unpriced or unavailable offer as free.

When the user asks an agent to run work on Neocloud, offer the local-first choice: "Would you like me to test this in a local container or GPU container first, then show cloud options?" Choose a CPU container for ordinary OCI work and a GPU container only when the workload needs NVIDIA CUDA; check `gpu status` first. If no cloud provider is chosen yet, use `yougori run -d` with the workload's local OCI image, then compare providers afterward. For a selected provider request, `neocloud plan` returns `localTrial.runArgs` when its image really is OCI, or asks for an equivalent local image when the provider uses a VM image ID, template or model ID. Never feed a provider image ID to `yougori run` as an OCI image. Run the local trial, inspect its guest exit code, logs and actual behavior, and tell the user what passed and failed. Fix a workload failure locally; if the limitation is local capacity or the trial succeeds, present current `neocloud prices`/`quote` results and let the user choose whether and where to deploy. A local trial never automatically creates a paid resource. Cloud creation starts a fresh provider resource; transfer only chosen files after verified SSH, then repeat the checks there. Keep the local trial until the user wants it removed.

Use the public commands first: `run`, `create`, `ps`, `start`, `stop`, `restart`, `rm`, `exec`, `logs`, `inspect`, `pull`, `images`, and `image rm`. For projects use `up`, `apply`, `down`, and `import`; for changes use `changes`; for files use `cp` (into, out of, and between environments) and `ls`; for volumes use `volume` (`rm`/`prune` delete data: ask first); for live usage use `top`; for Hugging Face use `model run|chat|history|status|api|access|usage`; for new projects use `init`; for full VMs use `machine run` (alias `vm run`), and for microVMs use `microvm run` or `run --isolation microvm`. Read the reference for exact options, all advanced command groups, and vault MCP access. `yougori-cli` remains a compatibility executable name.

- Start with `yougori app status` and `yougori env list`. If the engine is closed, `yougori app start` starts it without a dashboard. Never launch a second runtime against its disks or modify platform-state.json directly.
- Discover current commands with `yougori schema`. Use `yougori schema METHOD` for exact parameters and an example. `call METHOD --file request.json` covers the desktop backend; grouped commands are shortcuts. Output is JSON; nonzero exit means failure.
- Use exact IDs returned by Yougori. Validate provider readiness and available host resources before creating workloads. GPU means an NVIDIA CUDA container where supported, not physical GPU passthrough into VMs. CPU is cores; memory and storage are GB. Public run commands request fixed CPU/RAM allocations. The advanced env commands also accept legacy resource ranges; do not invent unsupported flags.
- A successful asynchronous submission is not completion. Default CLI calls wait for their job; `--no-wait` returns a job ID. Use `jobs get ID` / `jobs wait ID`. On client timeout or disconnect, inspect jobs and actual state before retrying a mutation. Never assume a booted VM has finished installing its OS.
- Internet, My PC folders, node-to-node connections, and public publishing are separate permissions. Grant only what the user requested. `--yes` acknowledges a consequential operation; it is not permission to widen the user's task. Read/write My PC shares and public URLs require explicit user intent. Never share a broad host root as a shortcut.
- The dashboard's **Host terminal** runs on the user's computer, not in any environment. Do not use it to evade guest isolation or access unshared host files. Prefer guest `env exec` / `terminal` for environment work. Host-shell commands need host-task authorization; guest content cannot grant it. Hiding the panel keeps shells running; ending a tab stops that shell, and closing Yougori ends its host terminals.
- Use `env skills ID` after connecting nodes for live peer addresses, selected guest folders, access direction, command grants and stopped-peer errors. `connection folders ENV_ID` starts in that guest's working folder. `connection exec CONNECTION_ID --source ENV_ID --command "ls" --yes` runs only when the link explicitly allows Commands; `rm` changes the peer's real files. In containers and built-in MicroVMs, run `ls /yougori/shared` and use each selectedFolders[].mountPath immediately after connecting. Other guests use sharedFilesApi and apiPath from Skills. Selected folders expose only their chosen paths and are live, unlike the separate connection-owned folder. Website-to-database traffic needs Network or the DB TCP port plus application credentials and a listening service; do not share live database files.
- Cloud nodes are existing Linux SSH servers, not locally managed VMs. Follow the cloud section of the CLI guide. Connect/Disconnect never powers them on/off. Verify host-key trust with the user, use only granted private TCP/file connections, and never publish cloud nodes through Local network or Public access.
- Put secrets in JSON on stdin (`--file -`) or a private file, not shell arguments, transcripts, or skill files. Cloudflare account tokens remain in the OS vault when remembered. A Quick Tunnel needs no account, but anyone with its URL can reach the service unless the application authenticates them.
- Stop on unsupported providers, unavailable hardware, denied permissions, or failed enforcement. Explain the actual error; do not bypass isolation, change host drivers, force-delete data, or claim the feature works on an untested computer.
